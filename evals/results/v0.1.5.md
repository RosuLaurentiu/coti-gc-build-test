**PRIVATE-JOB-1**

The first comparison does not isolate private eligibility. Both the public epoch and public readiness changed. The selected policy permits an early return for an idle job. The difference between 180 and 6 MPC calls therefore does not establish a privacy defect. Do not pad idle calls on this evidence.

The second fixture is a useful controlled comparison. It holds the stated public conditions constant and changes only private eligibility. It establishes local parity for the recorded ordered MPC operations, call roles, written slots and event schema. It also records a **38,000 gas difference**. That difference remains unexplained.

The mock uses clear values and ordinary internal branches. These can affect local gas. Fake ciphertext values can also affect storage costs and refunds. These are possible causes to investigate, not a demonstrated diagnosis. Do not label the difference either native leakage or harmless mock behavior without further evidence.

Proposed checks:

- Attribute the gas difference to the actual execution frames and instructions. Separate application behavior from mock internals, storage charges and refunds.
- Compare public return values, errors, event payloads and topics, external call order and arguments, storage access, transaction count and timing. Event names or schemas alone are insufficient.
- Check that ready jobs retain the prescribed capacity for both eligibility outcomes. Include relevant boundary inputs within the same public work class.
- If the application branches on eligibility in an observable way, correct that branch within the selected privacy policy. If the difference comes from mock internals, correct the mock or the interpretation of its results without claiming native privacy.
- Any later native assessment needs the exact candidate and equivalent public starting conditions. Structural parity alone cannot establish absence of all side channels.

The report can claim the supplied local structural observations and gas difference. It cannot claim privacy verified. No native receipt or native privacy result exists.

**PRIVATE-PAYMENT-1**

The acceptance predicate checks the wrong amount. The promise concerns recipient net units after the fee; the code checks gross units.

For gross `100`, the fee is `2` and the recipient receives `98`. The saved minimum of `97` passes both predicates and does not detect the defect. A minimum of `99` passes the current predicate but violates the recipient's signed guarantee.

The correction is:

```text
fee = floor(gross * 200 / 10000)
received = gross - fee
accept = existingValidConditions AND (received >= minimumReceived)
```

Keep the signed minimum unchanged. Reducing it automatically changes the recipient's authorization.

In the encrypted implementation, retain an encrypted acceptance condition. Apply it through the existing fixed-shape no-effect path. Do not decrypt it or introduce a secret-dependent public revert. Gate every asset debit, recipient credit, service credit and liability update consistently. Publicly invalid requests can retain their permitted revert behavior.

Also check:

- Zero inputs under the service's existing zero-payment policy; do not invent a new policy.
- Maximum supported values, intermediate multiplication width, subtraction and rounding. Encrypted arithmetic does not inherit Solidity's checked-arithmetic guarantees.
- Accepted conservation: escrow debit equals recipient credit plus service credit.
- Rejected conservation: asset balances, fee credits and liabilities remain unchanged.
- Correct encrypted selection in both outcomes, with the required observable work shape.
- Transfer or callback failure: no partial debit, payout or fee credit survives a failed transaction.

The fragment proves a defect in the supplied acceptance rule and supports the correction above. It does not prove that an encrypted implementation, token callback path or native transaction behaves correctly. No proposed check has been executed.

**PRIVATE-ESCROW-1**

The proposed cancellation returns principal but removes the means to complete three remaining obligations. It also allocates all native work escrow, leaving no cleanup reserve. Clearing the lock permits a new request to overwrite identities and revisions that cleanup still needs.

The required cancellation allocation is:

```text
11 = 1 cancellation-caller credit
   + 6 remaining cleanup reserve
   + 4 owner withdrawal credit
```

Crediting the owner `10` conflicts with the agreed cleanup reservation.

A bounded correction should:

- Abort further active work and return token principal once.
- Record that principal has been returned, so cancellation replay cannot return it again.
- Credit the cancellation caller `1` once, reserve `6`, and credit the owner's withdrawal balance `4`.
- Retain the reservation identities, revisions, cleanup progress and remaining reserve until the obligations are resolved.
- Keep the affected request locked against replacement while cleanup depends on its saved identity. The owner's permitted principal return and excess withdrawal must remain available.
- Advance cleanup progress and earn the applicable worker credit only for a successful cleanup. Release the request lock and remove recovery data only after all cleanup obligations are resolved. Unwithdrawn credits must survive that deletion.

If each successful cleanup earns its reserved `2`, the expected progression is:

| Successful cleanups | Remaining reservations | Cleanup reserve | Cumulative cleanup credits |
|---:|---:|---:|---:|
| 0 | 3 | 6 | 0 |
| 1 | 2 | 4 | 2 |
| 2 | 1 | 2 | 4 |
| 3 | 0 | 0 | 6 |

The caller credit remains `1` and the owner excess credit remains `4`. If credits are withdrawn during the sequence, reconcile actual native balance against outstanding credits and reserves; include completed withdrawals in the original `11`-unit conservation equation.

The receiver-revert test is essential. If the worker writes its next cursor and payment credit before calling the receiver, a revert propagated through the whole transaction must roll back those writes and all changes made by that transaction. **A caught receiver revert does not automatically undo earlier writes in the caller.** Either propagate failure or use a reviewed structure that leaves the failed attempt's cursor, credits, reserve and external reservation unchanged. Do not mark failed cleanup complete or pay it as successful.

Local acceptance checks should cover:

- Cancellation with zero, one, two and three remaining reservations, using the corresponding required reserve and excess.
- Exact principal return, native conservation and preserved withdrawal liabilities.
- Repeated cancellation, repeated cleanup and repeated withdrawals without double payment.
- Failure after cursor and credit writes, followed by a successful retry of the same saved reservation.
- Separate cleanup transactions: a failed later transaction must preserve earlier successful cleanups.
- Stale revisions, identity replacement attempts and conflicting new requests while recovery is pending.
- Reentrant receiver calls where applicable, without duplicate cleanup, payment or principal return.
- Final release only after all reservations are resolved; subsequent requests cannot alter old outstanding withdrawal credits.

The supplied design has supported funding and recovery-state defects. Its principal-only test does not accept the cancellation lifecycle. These are proposed local corrections and checks, not tested implementation or native results. Paid cleanup, the stage structure and the `1`/`2` constants belong to this synthetic protocol alone.
